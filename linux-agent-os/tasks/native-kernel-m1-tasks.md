# 任务清单：自研内核 第一里程碑 M1
版本：v0.3　日期：2026-11-02
规格：`specs/native-kernel-m1.md`（v0.3）　决定：`decisions/0004-m1-code-base-token-signature-capability.md`
说明：代码基础是现有 agent-first-os 代码。T-M1-0 到 T-M1-4 每个完成后，由验收审查先做阶段审查，通过后才进下一个任务，T-M1-5 仍统一验收；阶段审查不替代最终验收，按通用门槛核对本任务产出。每个任务的产出都要满足规格「验证方法」一节的通用门槛 1 到 11，下表「验收标准」只写本任务特有的部分，不重复门槛。每条「被拒、被拦、冻结后停止」类断言配对照组。证据状态以规格为准，没有运行日志的一律是「计划」。

## 已知失败（M1 不依赖，原因待查）
下列 8 项在实测里失败，M1 不做驱动、不写磁盘，不依赖它们。任何任务不得因为它们失败而改期望值，也不得把它们的失败当成 M1 的失败。来源是 `research/round5-afos-qemu-baseline.md`（验收审查有条件通过，没有复跑，仅为基线记录），失败原因都没有查明。
g6-virtio-net-rx、g6-virtio-net-tx、g6-virtio-block、g7-native-block-write、g7-native-block-flush、g7-native-block-read、g7-native-journal-recovery、g7-native-journal-commit-recovery。

第 9 项 g2-irq（定时器中断没送达）**不在此列**：M1 依赖定时器抢占，它由 T-M1-1 先查清。

## 范围提醒
M1 不做跨重启持久化：boot_generation 每次启动由内核重新生成，T-M1-4 的重放用例只覆盖同一次启动内，不得宣称防住跨重启重放；该项属里程碑 2。因此 T-M1-4 里「重启后提交上一轮令牌」一类子用例不在 M1。

## 备注
1. 「冻结」的含义：通用门槛 10 要求送审的产物冻结。T-M1-0 冻结的是默认构建的基线，后续任务在其上改动并各自产出新版本，最终送 T-M1-5 的是 T-M1-4 之后的版本，它也要重新冻结并附 SHA256SUMS。若总经理的意思是整个 M1 只冻结一次，请指出，本清单要改。
2. 阶段审查：T-M1-1 到 T-M1-4 每个完成后，验收审查先看一遍再进下一个，T-M1-5 统一验收（总经理决定）。T-M1-0 的冻结基线也先过一遍再进 T-M1-1（总经理决定）。
3. T-M1-2、T-M1-3、T-M1-4 的「先出方案」一步是为了不让实现者自行决定字段和错误码，与规格「接口」一节一致。
4. 过期用例的做法（总经理决定）：默认镜像里不放推进时钟的 syscall，过期用短 TTL 加真实等待，对照组是 TTL 内提交成功。这样过期项可以在默认单一镜像上验。风险：现有代码里 consume 的「时钟」是调用时才自增的计数器（只在 bound_status 为 OK 且未紧急暂停时），不是定时器驱动的，要先由 T-M1-3 的方案把它换成取自定时器计数的单调时钟；TCG 下 tick 速率不稳，所以用日志里的 tick 值判定。若 T-M1-1 最终没查明 g2-irq，过期项退到测试宏镜像并如实标注。
