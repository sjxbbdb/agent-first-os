## 已知失败（agent-first-os 实测，来源：`research/round5-afos-qemu-baseline.md`，TCG，QEMU 10.0.13，OVMF 2025.02）
逐项跑 95 项，86 项通过，9 项失败，失败都是测试断言失败，不是构建或启动失败。该报告已入库，验收审查核对过但没有复跑；其中失败原因都没有查明，下表「原因」只记报告里的现象。
| 项 | 现象 | M1 是否依赖 |
|----|------|-------------|
| g6-virtio-net-rx、g6-virtio-net-tx、g6-virtio-block | 串口里没有 `G6 virtio net transport READY`；QEMU 的 `info pci` 能看到设备 | 不依赖，M1 不做驱动和网络。原因待查 |
| g7-native-block-write、g7-native-block-flush、g7-native-block-read、g7-native-journal-recovery、g7-native-journal-commit-recovery | 串口出现 `SCHEDULER block device capability unavailable`，是上一行的连带结果 | 不依赖，M1 不写磁盘。原因待查 |
| g2-irq | 缺 `TIMER PREEMPT switched task`；`-d int` 里向量 0x20 和 0x08 在 5 秒内都是 0 次 | **依赖**：V2 的定时器抢占计数需要它。原因没查明，可能是代码问题，也可能是 TCG 时序或 QEMU 版本差异，未验证。T-M1-1 必须先查清，且要在 UEFI 路径上验证，并用同一 QEMU 参数下的最小程序能收到 IRQ0 作对照，否则按「未查明」处理 |

另外，实测时对拷贝做过三处调整：99 个 .sh 没有执行位、9 个 UEFI 测试写死 OVMF 路径、一个测试缺 `build/uefi` 目录；`run-all.sh` 原样跑会在第 2 项失败后退出。这些影响「别人原样复跑」，列入 T-M1-0。

## 目标（项目负责人已确认）
在 QEMU x86_64 UEFI（OVMF）里启动自研内核，证明四件事：内核能被固件接管并自报版本；两个任务能被定时器中断抢占调度；任务能通过结构化接口申请资源并被内核拒绝；外部动作必须经人工确认才放行。

## 范围（项目负责人已确认）
做什么：
- UEFI 启动进入内核，串口输出。
- 创建并调度两个任务，含定时器中断驱动的抢占。
- 任务通过结构化接口申请资源，内核可以拒绝并返回错误码。
- 一个需要人工确认才放行的模拟外部动作，及签名令牌校验。

不做什么：
- M1 默认镜像里内置的是测试公钥，对应的测试私钥在仓库里公开，只证明「验签机制能跑」，不证明密钥管理或确认端的安全；产品公钥和私钥的存放另议。
- action_nonce 的随机源：M1 用固定测试种子，明确标注不防预测，只证明机制；真正的随机源（见待定表）不在 M1 内。
- 不做驱动，不做网络栈，不写磁盘。
- 只在 QEMU 里验证。真机验证和任何写磁盘、改真机启动项的操作，必须先问项目负责人。
- 不证明安全性。验收只证明「在这套 QEMU 环境里、这些用例下成立」；需要绕过测试时，由验收审查另出对抗性用例清单。

## 接口
已定：令牌签名算法为 Ed25519；内核只持有公钥；私钥在确认端，不进内核镜像。
仍待写：结构化资源申请的请求与错误码字段、确认令牌的字段、模拟动作的记录行格式。字段名、取值范围和错误码不允许由实现者自行决定。做法与此前原型相同：T-M1-2、T-M1-3、T-M1-4 在动手实现前，先各写一份字段与错误码方案交总经理定，定稿后记入本节再实施。`research/round4-confirm-token-crypto.md` 第五节里的令牌用例和串口行格式（如 `CONFIRM verify case=...`、BAD_SIG、EXPIRED、REPLAY）只是调研的建议，定稿前不当成规格。

## 风险
- TCG 下的中断和调度时序不等于真机。
- 内核自己报计数器，计数器本身可能出错，所以被拦截用例要求计数器和日志行双重核对（见 V4）。
- 定时器中断在实测里没有送达（g2-irq 失败），原因未查明；若根因在内核代码，T-M1-1 的工作量未知。
- 现有代码有 46 个测试宏，没有默认单一镜像，T-M1-0 的工作量未知。
- Ed25519 验证在自研内核里的实际耗时没有实测；Monocypher 现版本未被审计覆盖。
- M1 不做跨重启持久化，重放防护只管同一次启动内；跨重启的重放和 boot_generation 持久化要到里程碑 2，之前不得宣称有。
- 时间基准是取自定时器计数的内核单调时钟，所以超时和过期都依赖定时器中断可用（T-M1-1）；时钟自增有条件，用例不能假设每次调用都 tick。过期用例靠真实等待，不加改时钟入口，所以过期项也能在默认单一镜像上验；代价是它依赖定时器可用，若 g2-irq 最终没查明，过期项退回测试宏镜像并如实标注。TCG 下 tick 速率不稳，用例按日志里打印的签发、截止、提交三个 tick 值判定，不按墙上时间判定。
- 能力撤销的资料未验证，但 M1 不做单独撤销，影响限于里程碑 2。

## 验证方法
### 一、通用门槛（验收审查口径，每个任务都要有，缺一项直接判不通过）
1. 源码在 git 里，送审版有提交号，并附产物 sha256 清单。送审后不得覆盖，要改就递增版本。
2. 完整构建日志，含构建命令、工具链版本、退出码。验收审查在干净目录复跑一次构建。
3. QEMU 完整命令行和串口全量日志落文件，用 `-serial file:` 或 `tee`，不接受截取片段。验收审查用同一命令复跑至少两次，两次输出一致（时间戳除外）。
4. 失败日志和成功日志都保留，不得覆盖。
5. 不得改期望值凑通过。用例与期望不符，如实报告，由验收审查判是缺陷还是规格问题。
6. 许可证：自研代码写明 SPDX；引入的第三方代码列出来源和许可证（EDK2、gnu-efi 一类要写清楚）。
7. 文档里不出现项目负责人的姓名。
8. 日志头必须写明：TCG 还是 KVM、OVMF 的版本与路径、内核版本与构建号。
9. 每条「被拒、被拦、冻结后停止」类断言必须配对照组：同一个动作在限制生效前先成功一次，否则「被拒」可能只是测试写错。
10. 送审的镜像和测试程序先冻结并附 SHA256SUMS，送审后不得覆盖；送审期间被改过的产物按不通过处理，改了就递增版本重送。
11. 前置条件：M1 验收必须基于默认构建的单一镜像（不靠测试宏拼出不同镜像），否则验收审查无法给出可复现的步骤。现状见 `research/round3-afos-baseline.md`，该条目前不满足，由 T-M1-0 解决。

### 二、第一里程碑的运行证据（QEMU x86_64 UEFI，OVMF）
用例编号为本规格暂定，期望值是草案；各用例由哪个任务产出见 `tasks/native-kernel-m1-tasks.md`。
证据状态一列的含义（v0.2 起新增「测试宏镜像已运行」一档，按验收审查的意见）：「计划」表示只有规格，没有任何运行证据；「已读源码」表示只在源码里看到相关实现，未运行；「测试宏镜像已运行」表示在测试宏拼出的镜像里有运行日志，只能说明构建和启动可行，不是默认单一镜像上的证据，不能当 M1 的运行证据，也不能当作已复核；「已运行」要附日志位置。当前没有一条经验收审查复跑的证据。

| 编号 | 内容 | 必须的证据 | 对照组 | 证据状态 |
|------|------|------------|--------|----------|
| V1a 固件交接与内核入口 | 固件把控制权交给内核，内核进入 C 入口 | 串口里有固件交接标记和内核入口标记；记录 OVMF 版本与路径 | 无需对照 | 测试宏镜像已运行（UEFI 链路，TCG；验收审查核对了报告与日志但没有复跑；不满足门槛 11） |
| V1b 版本与构建号 | 内核打印版本和构建号 | 串口里有内核版本行和构建号 | 无需对照 | 无证据：现有串口日志和 kernel.c 里都没有这一行，T-M1-0 要新增 |
| V2 双任务调度 | 两个任务输出交错，且至少一次靠定时器中断切换，不是任务主动让出 | 可检查的计数：各自运行次数、定时器抢占次数，不靠肉眼看交错 | 同一源码提交、仅关闭定时器抢占的另一个冻结构建（不用默认镜像里的运行期开关），计数应显示抢占次数为 0、只有主动让出 | 无运行证据：g2-irq 失败，定时器中断未送达，原因未查明（该失败的 trace 在 BIOS 路径，M1 走 UEFI，需在 UEFI 路径单独验证）；抢占默认只在测试宏下编译（已读源码） |
| V3 资源申请 | 成功和被拒各一条 | 被拒返回明确错误码；串口日志里有内核侧的拒绝记录 | 限额内的申请先成功一次，再超限被拒 | 计划（已读源码：内核无配额语义） |
| V4 人工确认，未确认被拦 | 没确认的外部动作被拦下 | 内核侧计数器为 0，且模拟动作的记录行在日志里确实不存在，两样都核对 | 同一动作经确认后放行（即 V5） | 计划 |
| V5 人工确认，确认后放行 | 确认后动作放行 | 计数器加一，且日志里出现带「模拟」字样的记录行 | 本身是 V4、V6、V7 的对照 | 计划 |
| V6 人工确认，超时或拒绝 | 超时或被拒绝后动作不发生 | 同 V4：计数器为 0 且记录行不存在 | 同一动作经确认后放行（即 V5） | 计划 |
| V7 令牌负面用例 | 签名错误、令牌过期、重放，各一条 | 每条都被拒绝，副作用证据同 V4；不只测正常路径 | 同一令牌第一次使用成功，再测重放；签名与过期各用对应的正常令牌作对照 | 计划（签名算法已定为 Ed25519；Monocypher 钉版本待定；签名项在跑通之前一律判未验证） |

V4、V5、V6 的最终证据必须在 T-M1-4 完成后的默认镜像上，用 Ed25519 签名令牌重跑；T-M1-3 阶段用的不带签名的模拟确认不得留在默认镜像里（可只存在于测试构建），阶段性的运行日志只能当过程记录，不能当 M1 的最终证据。
