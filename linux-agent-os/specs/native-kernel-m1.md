## 目标（项目负责人已确认）
在 QEMU x86_64 UEFI（OVMF）里启动自研内核，证明四件事：内核能被固件接管并自报版本；两个任务能被定时器中断抢占调度；任务能通过结构化接口申请资源并被内核拒绝；外部动作必须经人工确认才放行。

## 范围（项目负责人已确认）
做什么：
- UEFI 启动进入内核，串口输出。
- 创建并调度两个任务，含定时器中断驱动的抢占。
- 任务通过结构化接口申请资源，内核可以拒绝并返回错误码。
- 一个需要人工确认才放行的模拟外部动作，及签名令牌校验。

不做什么：
- M1 默认镜像里内置的是测试公钥，对应的测试私钥在仓库里公开，只证明「验签机制能跑」，不证明密钥管理或确认端的安全；产品公钥和私钥的存放另议。
- action_nonce 的随机源：M1 用固定测试种子，明确标注不防预测，只证明机制；真正的随机源（见待定表）不在 M1 内。
- 不做驱动，不做网络栈，不写磁盘。
- 只在 QEMU 里验证。真机验证和任何写磁盘、改真机启动项的操作，必须先问项目负责人。
- 不证明安全性。验收只证明「在这套 QEMU 环境里、这些用例下成立」；需要绕过测试时，由验收审查另出对抗性用例清单。

### T-M1-2 结构化资源申请接口（草拟，未定稿）
状态：**草拟，不是定稿**。来源是 T-M1-2 的方案草稿（执行代理只读调研，没有构建、没有运行任何东西）加总经理转达的字段决定。实施方正在出 v2，会新增整数回绕、内核地址、跨界三个畸形用例并重算计数，v2 出来后我按 v2 对一次本节再请总经理定稿。定稿前不得实施。本节所有内容的证据状态都是「计划」；其中引用的源码位置是方案草稿读 8fb9198 的结果，我没有核对。

**调用约定**
- syscall 号 49（`SYS_RESOURCE_REQUEST`）。方案草稿读 8fb9198 的 `syscall.h`，最大号是 48，49 空闲；0x7f 是现有「未知号」测试占用的，不能占。
- `int 0x80`，`rax=49`，`rdi` 为用户态请求结构地址，`rsi` 为结构长度，必须正好是 32。
- 返回 `rax`：成功 0，失败为负的 errno 风格值。
- 内核先检查 `rdi` 起 32 字节是否是该任务可读的用户内存，再把 32 字节整体拷进内核栈，之后只校验内核栈上的副本，不在用户内存上边读边判。

**请求结构 `AfosResourceRequest`**（小端，x86_64 原生，32 字节，8 字节对齐；前 8 字节复用现有的 `AbiHeader`）
| 偏移 | 宽度 | 字段 | 合法值 | 非法值 → reason |
|---|---|---|---|---|
| 0 | u16 | version | 1 | 0 → `VERSION_MISSING`；大于等于 2 → `VERSION_RANGE` |
| 2 | u16 | size | 32 | 其他 → `SIZE_RANGE` |
| 4 | u32 | flags | 0 | 非 0 → `FLAGS_NONZERO` |
| 8 | u32 | kind | 1（`AFOS_RES_KIND_PAGE`） | 0 → `KIND_MISSING`；大于等于 2 → `KIND_UNKNOWN` |
| 12 | u32 | count | 1 到 4（单次上限） | 0 → `COUNT_MISSING`；大于 4 → `COUNT_RANGE` |
| 16 | u64 | request_id | 非 0，任务自定，只用来让日志与用例一一对应 | 0 → `REQID_MISSING` |
| 24 | u64 | reserved | 0 | 非 0 → `RESERVED_NONZERO` |

「字段缺失」的定义：结构定长，没有可选字段，所以缺失只有两种：传入长度不是 32（记 `LEN`），或 version、kind、count、request_id 四个必填字段为 0（各有独立的 `*_MISSING`）。

**校验顺序**（固定；多个错误同时存在时只报第一个，畸形用例每次只改一个字段）：LEN，FAULT，VERSION，SIZE，FLAGS，KIND，COUNT，REQID，RESERVED，QUOTA。

**错误码**（errno 风格返回值加日志里的 reason 区分，不是每个 reason 一个独立负码）
| rc | 含义 | reason |
|---|---|---|
| 0 | 批准 | 无 |
| -14（EFAULT） | `rdi` 起 32 字节不是该任务可读的用户内存 | `FAULT` |
| -22（EINVAL） | 畸形：LEN、VERSION_MISSING、VERSION_RANGE、SIZE_RANGE、FLAGS_NONZERO、KIND_MISSING、COUNT_MISSING、COUNT_RANGE、REQID_MISSING、RESERVED_NONZERO | 见上表 |
| -95（EOPNOTSUPP） | kind 非 0 但内核不认识 | `KIND_UNKNOWN` |
| -122（EDQUOT） | 格式合法，但已用页数加 count 超过限额 | `QUOTA` |
| -12（ENOMEM） | 限额内但内核页池已空，不是配额拒绝 | `NOMEM` |
一次申请要么全批要么全拒，不做部分批准；被拒时已用页数不变，也不分配任何东西。`NOMEM` 在 M1 的用例里不触发（仅任务 A 申请，总量不会超过池）；它的错误路径因此没有运行用例覆盖，不得写成已验证。

**限额来源与数值**
- 限额是任务的属性：任务创建时由内核传入（任务描述里新增页配额字段，由创建函数记入任务对象），取编译常量 16。M1 不允许 Ring 3 自己指定限额。
- 数值：每任务页配额 16，单次申请上限 4，内核专用页池 32 页。若新增 BSS 顶到镜像布局边界（`__kernel_bss_end` 与用户代码起点的断言），降为 8、4、16，**先报告再改**，用例数与期望计数同步重算。该边界是否被顶到未验证。

**资源形态**（只能这样写）：记账型页配额。批准时从内核专用页池取空页、清零、记归属，页归内核记账给该任务，**任务不能访问这些页**；M1 不释放，配额按任务存活期累计。不得写成「内存分配已实现」「资源回收已实现」，也不得把任务 B 的已用页为 0 当成跨任务隔离的证据。

**日志三种行格式**（数字一律十进制；task 取从 1 起的槽位号；读不到结构体的 LEN 和 FAULT 两类，未知字段打印 `-`）
- 批准：`RES grant task=%u req=%u kind=%u count=%u used=%u quota=%u`（used 为批准后的值）
- 拒绝：`RES deny task=%u req=%u kind=%u count=%u used=%u quota=%u reason=%s rc=-%u`（used 为未变的值）
- 计数：`RES counts: req=%u grant=%u deny=%u deny_quota=%u deny_inval=%u deny_kind=%u deny_fault=%u deny_nomem=%u pages[1]=%u pages[2]=%u`；其中 `deny = deny_quota + deny_inval + deny_kind + deny_fault + deny_nomem`，`req = grant + deny`。打印时机：与 `SCHED counts` 同一风格，全部任务退出时一次，空闲 tick 检查后一次，共 2 行。
- Ring 3 任务用 SYS_WRITE 打印的 `M1 RES case=<ID> rc=<十进制有符号>` 只是辅助，拒绝的证据以内核行和计数为准，不以任务自述为准。

**证据判定规则**（实施与验收都按这个）：只认 `RES ` 前缀的行和 `RES counts:`；rc 必须来自 49 号路径，日志里不得出现 -38 与 `unknown number`；每条拒绝都要同时满足「计数、日志行、已用页数不变」三样一致且有对照的批准；在默认镜像上跑，构建不带任何测试宏；附源码检索证明新路径不在任何测试宏条件编译之内。已有的「资源用完被拒」类现象（IPC 端点池满、能力表满、共享内存满、令牌表满、重启被拒、冻结、未知号、写错误地址、页表池满）都不能当本任务的证据。

**已知限制**
- M1 不做「通用 Ring 3 任务创建」：只做内核内的创建函数（带配额参数），任务 A、B 经它创建；Ring 3 的任务创建入口放里程碑 2。
- 只有任务 A 申请，B 不调用 49，以免抢占造成 RES 行交错；所以跨任务的配额独立性没有被证明。
- 全部在 TCG 下，不外推到 KVM 或真机。
- 新增号和结构会让默认镜像哈希必然改变，需要重新冻结、重出 SHA256SUMS；T-M1-1 的关抢占对照构建如仍要作 V2 对照，需同一提交重新冻结。
- 号的合入顺序：48（`SYS_CLOCK_TICKS`，T-M1-1）先于 49；方案草稿说 GitHub 上的内核代码尚未合入 T-M1-1，合并顺序错了会冲突。

**方案草稿里仍属倾向、总经理尚未明确决定的点**（我没有看到明确的决定，列出供定稿时逐条确认，不当成已定）：基线用 T-M1-1 的 8fb9198（而不是严格按清单用 T-M1-0）；畸形用例 M01 到 M12 是否全做，还是只做字面要求的「缺失、越界」最小集；`M1 RES case=` 辅助行是否保留。

**用例与期望计数**：方案草稿的 K01 到 K12 对照、M01 到 M12 畸形、Q01 限额内到上限、Q02 超限被拒，共 26 次申请，期望 `RES counts: req=26 grant=13 deny=13 deny_quota=1 deny_inval=10 deny_kind=1 deny_fault=1 deny_nomem=0 pages[1]=16 pages[2]=0`。这是**旧版**，v2 会加整数回绕、内核地址、跨界三个畸形用例，计数要重算，请以 v2 为准，本节在对表后更新。逐字的期望行不抄进规格，留在方案文件和检查脚本里，改期望值必须先报。

## 风险
- TCG 下的中断和调度时序不等于真机。
- 内核自己报计数器，计数器本身可能出错，所以被拦截用例要求计数器和日志行双重核对（见 V4）。
- 定时器中断在实测里没有送达（g2-irq 失败），根因已查明（TCG 下，测试等待窗口短于 PIT 周期），KVM 未测，换成 KVM 后是否仍成立没有证据。V2 仍是「无运行证据」，直到默认镜像上抢占计数大于 0，且关抢占的对照构建为 0。
- 现有内核只处理来自 Ring 3 的向量 32（kernel.c:1357），内核态 IF 恒为 0，idle 是 `cli; hlt`，任务退出后 tick 就停。若不改，TTL 真实等待用例没有时钟可读。T-M1-1 与 T-M1-3 的验收都要证明：idle 和等待期间内核照常收 tick（idle 改成 `sti; hlt` 一类做法，向量 32 在 Ring 0 到达不能落进异常路径），用计数证明。这是验收审查提的 D1，对 M1 影响最大。
- 现有代码有 46 个测试宏，没有默认单一镜像，T-M1-0 的工作量未知。
- Ed25519 验证在自研内核里的实际耗时没有实测；Monocypher 现版本未被审计覆盖。
- M1 不做跨重启持久化，重放防护只管同一次启动内；跨重启的重放和 boot_generation 持久化要到里程碑 2，之前不得宣称有。
- 时间基准是取自定时器计数的内核单调时钟，所以超时和过期都依赖定时器中断可用（T-M1-1）；时钟自增有条件，用例不能假设每次调用都 tick。过期用例靠真实等待，不加改时钟入口，所以过期项也能在默认单一镜像上验；代价是它依赖定时器可用，若 idle 与等待期间收 tick 最终做不到，过期项退回测试宏镜像并如实标注。TCG 下 tick 速率不稳，用例按日志里打印的签发、截止、提交三个 tick 值判定，不按墙上时间判定。
- boot_generation 在 M1 是固定测试值，同一值在每次启动都相同，所以跨重启的令牌在 M1 里不会因 boot_generation 被拒，M1 不得宣称防住跨重启重放，不得拿它当「重放防护已验证」的依据。
- action_nonce 在 M1 用固定测试种子，可预测，只证明机制。
- 能力撤销的资料未验证，但 M1 不做单独撤销，影响限于里程碑 2。

## 验证方法
### 一、通用门槛（验收审查口径，每个任务都要有，缺一项直接判不通过）
1. 源码在 git 里，送审版有提交号，并附产物 sha256 清单。送审后不得覆盖，要改就递增版本。
2. 完整构建日志，含构建命令、工具链版本、退出码。验收审查在干净目录复跑一次构建。
3. QEMU 完整命令行和串口全量日志落文件，用 `-serial file:` 或 `tee`，不接受截取片段。验收审查用同一命令复跑至少两次，两次输出一致（时间戳除外）。
4. 失败日志和成功日志都保留，不得覆盖。
5. 不得改期望值凑通过。用例与期望不符，如实报告，由验收审查判是缺陷还是规格问题。
6. 许可证：自研文件写明 SPDX 为 `MIT`（决定 0005：整个仓库按 MIT，根目录有 `LICENSE`；例外与执行记录见 `specs/license-mit-rollout.md`）；基于 Linux 源码的补丁保持 GPL-2.0-only；引入的第三方代码列出来源和许可证（EDK2、gnu-efi 一类要写清楚）。
7. 文档里不出现项目负责人的姓名。
8. 日志头必须写明：TCG 还是 KVM、OVMF 的版本与路径、内核版本与构建号。
9. 每条「被拒、被拦、冻结后停止」类断言必须配对照组：同一个动作在限制生效前先成功一次，否则「被拒」可能只是测试写错。
10. 送审的镜像和测试程序先冻结并附 SHA256SUMS，送审后不得覆盖；送审期间被改过的产物按不通过处理，改了就递增版本重送。
11. 前置条件：M1 验收必须基于默认构建的单一镜像（不靠测试宏拼出不同镜像），否则验收审查无法给出可复现的步骤。现状见 `research/round3-afos-baseline.md`，该条目前不满足，由 T-M1-0 解决。

### 二、第一里程碑的运行证据（QEMU x86_64 UEFI，OVMF）
用例编号为本规格暂定，期望值是草案；各用例由哪个任务产出见 `tasks/native-kernel-m1-tasks.md`。
证据状态一列的含义（v0.2 起新增「测试宏镜像已运行」一档，v0.5 起新增「另一构建已运行」，均按验收审查的意见）：「计划」表示只有规格，没有任何运行证据；「已读源码」表示只在源码里看到相关实现，未运行；「另一构建已运行」只用于对照组：对照构建是对照，不是被验证对象，和门槛 11 不冲突，但它的运行不能当被验证对象的证据；「测试宏镜像已运行」表示在测试宏拼出的镜像里有运行日志，只能说明构建和启动可行，不是默认单一镜像上的证据，不能当 M1 的运行证据，也不能当作已复核；「已运行」要附日志位置。当前没有一条经验收审查复跑的证据。

| 编号 | 内容 | 必须的证据 | 对照组 | 证据状态 |
|------|------|------------|--------|----------|
| V1a 固件交接与内核入口 | 固件把控制权交给内核，内核进入 C 入口 | 串口里有固件交接标记和内核入口标记；记录 OVMF 版本与路径 | 无需对照 | 测试宏镜像已运行（UEFI 链路，TCG；验收审查核对了报告与日志但没有复跑；不满足门槛 11） |
| V1b 版本与构建号 | 内核打印版本和构建号 | 串口里有内核版本行和构建号 | 无需对照 | 无证据：现有串口日志和 kernel.c 里都没有这一行，T-M1-0 要新增 |
| V2 双任务调度 | 两个任务输出交错，且至少一次靠定时器中断切换，不是任务主动让出；等待用「收到至少 N 次 tick 再退出」，N 事先在方案里定，不用固定循环次数；idle 与等待期间内核照常收 tick（验收审查 D1），用计数证明；「TIMER PREEMPT」打印次数的口径由 T-M1-1 方案先定，**已定（总经理批准，2026-11-02，经总经理转达记录）**：默认镜像不再逐次打印，只输出 `SCHED counts` 汇总行（各任务运行次数、定时器抢占次数、主动让出次数等计数），测试宏构建保留旧的逐次打印；以下是定之前的背景（报告观察到 Ring 3 期间收到 50 次 0x20 却只打印 1 次，原因是只有存在另一个可运行任务才切换并打印，该解释报告自己说没深查），定稿记入规格 | 可检查的计数：各自运行次数、定时器抢占次数，不靠肉眼看交错 | 同一源码提交、仅关闭定时器抢占的另一个冻结构建（附 SHA256SUMS，不用默认镜像里的运行期开关），计数应显示抢占次数为 0、只有主动让出；该构建的证据状态记「另一构建已运行」，它是对照，不是被验证对象 | 无运行证据：g2-irq 失败，定时器中断未送达，原因未查明（该失败的 trace 在 BIOS 路径，M1 走 UEFI，需在 UEFI 路径单独验证）；抢占默认只在测试宏下编译（已读源码） |
| V3 资源申请 | 成功和被拒各一条 | 被拒返回明确错误码；串口日志里有内核侧的拒绝记录 | 限额内的申请先成功一次，再超限被拒；畸形请求配对照组 | 计划（已读源码：内核无配额语义；接口见「接口」节，草拟未定稿） |
| V4 人工确认，未确认被拦 | 没确认的外部动作被拦下 | 内核侧计数器为 0，且模拟动作的记录行在日志里确实不存在，两样都核对 | 同一动作经确认后放行（即 V5） | 计划 |
| V5 人工确认，确认后放行 | 确认后动作放行 | 计数器加一，且日志里出现带「模拟」字样的记录行 | 本身是 V4、V6、V7 的对照 | 计划 |
| V6 人工确认，超时或拒绝 | 超时或被拒绝后动作不发生 | 同 V4：计数器为 0 且记录行不存在 | 同一动作经确认后放行（即 V5） | 计划 |
| V7 令牌负面用例 | 签名错误、令牌过期、重放，各一条；无签名令牌三种构造（令牌缺失、签名全零、alg 不是 Ed25519）各一条；boot_generation 缺失、boot_generation 不匹配各一条 | 每条都被拒绝，副作用证据同 V4；不只测正常路径 | 同一令牌第一次使用成功，再测重放；签名与过期各用对应的正常令牌作对照；无签名三种构造的对照是同一动作带有效签名令牌放行；boot_generation 两条的对照是带正确 boot_generation 的同一令牌放行 | 计划（签名算法已定为 Ed25519；Monocypher 钉版本待定；签名项在跑通之前一律判未验证） |

V4、V5、V6 的最终证据必须在 T-M1-4 完成后的默认镜像上，用 Ed25519 签名令牌重跑；T-M1-3 阶段用的不带签名的模拟确认不得留在默认镜像里（可只存在于测试构建），阶段性的运行日志只能当过程记录，不能当 M1 的最终证据。
