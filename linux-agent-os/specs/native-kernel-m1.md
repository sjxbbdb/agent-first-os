版本：v0.1（骨架）　日期：2026-11-02　状态：草稿，里程碑内容为「草案待项目负责人确认」

## 目标（草案待项目负责人确认）
在 QEMU x86_64 UEFI（OVMF）里启动自研内核，证明四件事：内核能被固件接管并自报版本；两个任务能被定时器中断抢占调度；任务能通过结构化接口申请资源并被内核拒绝；外部动作必须经人工确认才放行。

## 范围（草案待项目负责人确认）
做什么：
- UEFI 启动进入内核，串口输出。
- 创建并调度两个任务，含定时器中断驱动的抢占。
- 任务通过结构化接口申请资源，内核可以拒绝并返回错误码。
- 一个需要人工确认才放行的模拟外部动作，及签名令牌校验。

不做什么：
- 不做驱动，不做网络栈，不写磁盘。
- 只在 QEMU 里验证。真机验证和任何写磁盘、改真机启动项的操作，必须先问项目负责人。
- 不证明安全性。验收只证明「在这套 QEMU 环境里、这些用例下成立」；需要绕过测试时，由验收审查另出对抗性用例清单。

## 接口
待写。结构化资源申请的请求与错误码字段、确认令牌的字段、模拟动作的记录行格式，要等抽象对象的取舍定了再定。每一项在 v0.2 里要写明字段、取值范围和错误码，不允许由实现者自行决定。

## 风险
- 里程碑内容未经项目负责人确认，规格可能整体改动。
- TCG 下的中断和调度时序不等于真机。
- 内核自己报计数器，计数器本身可能出错，所以被拦截用例要求计数器和日志行双重核对（见 V4）。
- 令牌校验的密码原语未调研。
- 能力撤销的资料未验证。

## 验证方法
### 一、通用门槛（验收审查口径，每个任务都要有，缺一项直接判不通过）
1. 源码在 git 里，送审版有提交号，并附产物 sha256 清单。送审后不得覆盖，要改就递增版本。
2. 完整构建日志，含构建命令、工具链版本、退出码。验收审查在干净目录复跑一次构建。
3. QEMU 完整命令行和串口全量日志落文件，用 `-serial file:` 或 `tee`，不接受截取片段。验收审查用同一命令复跑至少两次，两次输出一致（时间戳除外）。
4. 失败日志和成功日志都保留，不得覆盖。
5. 不得改期望值凑通过。用例与期望不符，如实报告，由验收审查判是缺陷还是规格问题。
6. 许可证：自研代码写明 SPDX；引入的第三方代码列出来源和许可证（EDK2、gnu-efi 一类要写清楚）。
7. 文档里不出现项目负责人的姓名。
8. 日志头必须写明：TCG 还是 KVM、OVMF 的版本与路径、内核版本与构建号。

### 二、第一里程碑的运行证据（QEMU x86_64 UEFI，OVMF）
用例编号为本规格暂定，期望值是草案。
| 编号 | 内容 | 必须的证据 |
|------|------|------------|
| V1 启动 | 固件把控制权交给内核，内核打印版本和构建号 | 串口里有固件交接标记和内核版本行；记录 OVMF 版本与路径 |
| V2 双任务调度 | 两个任务输出交错，且至少一次靠定时器中断切换，不是任务主动让出 | 可检查的计数：各自运行次数、定时器抢占次数，不靠肉眼看交错 |
| V3 资源申请 | 成功和被拒各一条 | 被拒返回明确错误码；串口日志里有内核侧的拒绝记录 |
| V4 人工确认，未确认被拦 | 没确认的外部动作被拦下 | 内核侧计数器为 0，且模拟动作的记录行在日志里确实不存在，两样都核对 |
| V5 人工确认，确认后放行 | 确认后动作放行 | 计数器加一，且日志里出现带「模拟」字样的记录行 |
| V6 人工确认，超时或拒绝 | 超时或被拒绝后动作不发生 | 同 V4：计数器为 0 且记录行不存在 |
| V7 令牌负面用例 | 签名错误、令牌过期、重放，各一条 | 每条都被拒绝，副作用证据同 V4；不只测正常路径 |
